# Crank health

Measure, then plan. `scripts/health.py` produces the evidence: it inventories the repo, chooses each project's analyzers, runs them, and writes every finding in one schema with a first letter per category. You read the repo, rule on what the tools got wrong, and write a plan of tasks a coding agent can work and verify. Grades follow `references/grading.md`, the plan fills `assets/plan.md`.

`scripts/`, `references/` and `assets/` are relative to this skill's directory, and `health.py` below stands for `python3 <this skill's directory>/scripts/health.py`. It needs Python 3.11; on an older `python3` run it as `uv run --python 3.12 <this skill's directory>/scripts/health.py`. The target path defaults to the current repo. Quick profile unless `--deep`. `--only <category,…>` narrows the categories; the rest read `not assessed (not selected)`. `--project` repeats; the selection is the union, the rollup covers the selection only, and repo-wide tools run over the selected directories.

Every project is its own unit, so a monorepo is N projects plus the rollup.

## Contracts

- **Zero footprint.** The scan writes under the run dir `<repo>/.crank-health/<YYYY-MM-DD>-<4 hex>/` and a temp dir it deletes, and creates `.crank-health/.gitignore` containing `*` only when none exists; another run's dir beside yours is not yours to touch. Whatever you run yourself (a deep tool, a Verify command) writes under `<run-dir>/scratch/`. `health.py finish` must come back clean before you report.
- **Secrets never quoted.** The scan saves no secret value and no source excerpt, and a secret finding anchors on the rule id and the file, never the flagged line. Keep it that way in the plan and in your reply.
- **Quick never executes repo code.** Build, test and mutation tools run only under `--deep`, and mutation tools only where the repo owns and installed them (an ephemeral copy fails confidently instead of saying "not available").
- **One tool never aborts the run.** A tool that fails records one of the five states in [references/run-dir.md](references/run-dir.md) and the scan continues.
- **Nothing to measure is `not assessed (reason)`, never A.** All eight categories appear in every report.

## Steps

- [ ] 1. **Scan.** `health.py scan [path]`, passing `--pr`, `--deep`, `--only` and `--project` through. It prints the run dir, the first grade line, every row that did not end `ok`, and each `check:` line. Then read `inventory.md`, `tools.md`, `grades.md` and `summary/`; [references/run-dir.md](references/run-dir.md) says what each file holds and how to rule on it, rerun a tool, and pass a tool one more argument. Done when every `error`, `timeout` and `check:` row is resolved by a rerun or named in the plan with its reason (on the Not assessed line when it leaves a category unmeasured, beside the category's basis when a standby graded it), and every `not-available` row has its install hint there.
- [ ] 2. **Triage.** Read the repo before you believe a tool: knip on a library, ty on untyped code, jscpd on a test suite, zizmor on unpinned actions, and above all whether the code under scan is a fixture, a captured snapshot or deliberately broken (`inventory.md` lists snapshot dirs and generated files, and the `test`, `snapshot` and `generated` flags mark their findings; a README or test beside the files usually says). Read the reference for each language the scan found (`references/jsts.md`, `python.md`, `go.md`, `csharp.md`, `cpp.md`) and `references/common.md`: each says what its tools get wrong. Rule with `health.py verdict`, a reason on every ruling: `--dropped` for a false positive or a load-bearing fixture, `--advisory` for a real finding that is not this repo's to count, `--graded` to promote one. Findings in generated code (`dist/`, `gen/`, `*.gen.*`, lockfiles, captured tool output, globs the repo's own Biome or fallow config excludes) get no task and stay in the count. Vendored code the repo's own linter or formatter ignores (a copied UI kit under `components/ui`) is one ruling by path. Done when every finding the plan will cite or leave out is graded, advisory, or dropped with a reason.
- [ ] 3. **Grade.** `health.py grade <run-dir>` prints every project and the rollup with the arithmetic beside each letter. Under `--deep`, grade the categories your deep tools measured by hand from `references/grading.md`, printing the same arithmetic. Done when every project and the rollup carry all eight categories, each with a letter and its basis or `not assessed (reason)`.
- [ ] 4. **Plan.** Fill `assets/plan.md` into `<run-dir>/plan.md`. Theme tasks (one rule across files is one task; two categories at the same place merge into one task titled with both), order by letters moved then category order (security, types, dead code, complexity, duplication, lint, format, test quality), cap at 20 and spill the rest to `<run-dir>/findings.md` (no file when nothing spills). Every task carries the exact tool command that reports zero when it is done: copy the tool's command from `tools.md` → Commands, which names its pinned version and its cwd, and add the filter that isolates the task. An `aislop` or `gitleaks` command there names the repo where the scan read a copy of the in-scope files, so it also reports ignored paths. When the zero is a ruling the scan makes rather than the tool's own output (a vulnerable package that should move to `devDependencies`), the Verify command is `health.py rerun <run-dir> --tool <name>`, which prints the graded count. Run a Verify command once before you write it down. A fixture whose findings are load-bearing is named as such at the top and gets no task. Done when every graded finding in hand-written code is in a task or the spill file.
- [ ] 5. **Fix** (only with `--fix`). Run the repo's own formatter with its write flag (`prettier --write`, `biome format --write`, `oxfmt --write`, `ruff format`, `gofmt -w`, `dotnet format whitespace`, `clang-format -i`), then the safe autofixes (`ruff check --fix` without `--unsafe-fixes`, `eslint --fix`, `oxlint --fix`, `biome lint --write`), with the repo's config only; a repo with no formatter keeps its style, and fixtures named in the plan are left alone. `health.py rerun <run-dir> --tool <name>` runs the touched tools again, keeps your verdicts and re-grades. Then work the tasks in order, one task per commit-sized change, verifying each with its Verify command. Done when the rerun agrees with the plan's expected grades, or the remaining tasks are listed with why they were left.
- [ ] 6. **Report.** `health.py finish <run-dir>` deletes `scratch/`, greps the run dir for secret patterns and compares the footprint; delete and redact what the grep names, and remove a path the scan left behind (gitignore it when the repo's own tool wrote it). Reply with the grade line, the top three tasks, what was not assessed and why, and the run dir path. Done when `finish` exits 0 and you have accounted for every path it lists as written since the scan started.

## PR mode (`--pr <base>`)

`health.py scan --pr <base>` scans head, then the merge-base in a worktree outside the repo that borrows the head's `node_modules` and virtualenv, with the tool versions head ran, and removes the worktree. It compares finding sets keyed on (category, tool/rule, file after rename mapping, message with numbers masked): `new-findings.tsv` is head minus base, `resolved-findings.tsv` base minus head, and `pr.md` holds the delta per category. Whole-tree measures (duplication, dead code) are computed on both sides in full. Tasks come from new findings only; a new finding on a line the diff touched carries the `touched` flag and goes first. The base side is scanned as the base owned it: a formatter or linter the PR adopts makes every finding of the tool it replaced `resolved` and every finding of the new one `new`, so say that in the plan instead of counting it as churn. Under `--deep`, mutate only the changed files.

## Deep profile (`--deep`)

Adds: C# build-backed categories (`references/csharp.md`), C/C++ compile-database categories (`references/cpp.md`, a CMake or Meson configure into scratch), mutation testing where owned, coverage as context. The scan lists each deep tool as a row reading `deep tool: run it from references/<language>.md` and runs none of them: they execute the repo's build and tests, so you run them, one at a time, from that reference. Mutation runs in every project that owns a tool, 15 min each; `--project` is the cost control. Warn before cosmic-ray (it mutates files in place) and refuse it on a dirty tree. Budgets for what you run yourself: 300 s for build tools, 15 min for mutation, enforced with `perl -e 'alarm shift; exec @ARGV' <secs> <command…>` (macOS has no `timeout`); a killed tool is `timeout`.

## Gotchas

- A standby that graded because the owner errored says so in the plan: `oxlint graded lint on its default config because eslint reported error`.
- Versions float, so two runs a month apart can differ. `tools.md` records every version, and `rerun` and the base side of `--pr` reuse them, which is what lets a reader tell drift from change.
- `ok` is not `measured`: read every `check:` line and every Notes line before you trust a clean row.
